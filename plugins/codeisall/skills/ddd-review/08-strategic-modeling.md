# 战略设计建模标准

> 本文件定义战略设计文档的产出物规格和评判规则。
> 建模 AI 按规格产出文档，检查 AI 按评判规则逐条验证。

---

## 产出物规格

战略设计文档必须包含以下五个部分，每个部分的字段均为必填。

### 一、Context 清单

| 字段 | 说明 | 示例 |
|------|------|------|
| 名称 | Context 的英文标识（snake_case） | `order` |
| 中文名 | 业务方能理解的名称 | 订单 |
| 职责描述 | 一句话说清楚这个 Context 做什么 | 管理订单从创建到完成的生命周期 |
| 领域类型 | core / supporting / generic | core |
| 领域类型判定理由 | 为什么是这个类型 | 订单是平台核心交易能力，直接决定营收 |
| 不负责什么 | 明确排除的职责（至少 2 项） | 不负责支付收款、不负责物流追踪 |

### 二、统一语言表

每个 Context 必须有自己的术语表。

| 字段 | 说明 | 示例 |
|------|------|------|
| 术语 | 业务概念名称 | 订单 |
| 所属 Context | 该术语在哪个 Context 中定义 | order |
| 定义 | 在该 Context 中的精确含义 | 买家的一次购买行为，包含商品明细和收货信息 |
| 易混淆项 | 其他 Context 中相似但不同的概念 | payment Context 中的"交易"不是订单，是资金流转记录 |

### 三、Context 关系表

每对有关系的 Context 必须显式列出。

| 字段 | 说明 | 可选值 |
|------|------|--------|
| 上游 Context | 提供能力的一方 | - |
| 下游 Context | 消费能力的一方 | - |
| 关系类型 | DDD 标准关系 | customer-supplier / conformist / anticorruption-layer / shared-kernel / open-host-service / published-language / separate-ways |
| 集成方式 | 技术实现 | event（异步事件）/ api（同步调用）/ shared-db（共享数据库，需说明理由） |
| 数据流向 | 什么数据从上游到下游 | OrderPlaced 事件携带 order_id, user_id, total_amount |
| 失败策略 | 下游不可用时上游的行为 | 上游不感知（事件异步）/ 上游降级 / 上游阻塞 |

### 四、Context 路由规则

用于判断一个需求应该归属哪个 Context。

| 字段 | 说明 | 示例 |
|------|------|------|
| 业务动作/关键词 | 需求中出现的动作或名词 | 下单、加购物车、改收货地址 |
| 归属 Context | 该动作属于哪个 Context | order |
| 不归属（易混淆） | 容易误判的 Context + 原因 | 不是 payment（订单不管收钱） |

### 五、领域类型分布评估

| 字段 | 说明 |
|------|------|
| 核心域列表 | 哪些 Context 是核心域 |
| 核心域投入原则 | 核心域应该投入最多建模精力，使用最精细的战术设计 |
| 通用域处理方式 | 用成熟方案/第三方服务/简单 CRUD，不过度设计 |
| 支撑域处理方式 | 保证正确即可，不需要复杂建模 |

## 评判规则

检查 AI 按以下规则逐条验证，每条给出 pass / fail / warning。

### 完备性检查

| 规则编号 | 规则 | 判定方法 |
|---------|------|---------|
| STR-01 | 需求中的每个业务概念都归属了某个 Context | 提取需求中所有名词和动作 → 逐个检查是否出现在 Context 清单或路由规则中 → 未覆盖则 fail |
| STR-02 | 每个 Context 至少有 3 个路由规则条目 | 数路由规则表中每个 Context 的条目数 → <3 则 warning（可能职责不清） |
| STR-03 | 每个 Context 的"不负责什么"至少 2 项 | 数"不负责什么"字段的条目数 → <2 则 fail |

### 单一归属检查

| 规则编号 | 规则 | 判定方法 |
|---------|------|---------|
| STR-04 | 同一个业务概念只归属一个 Context | 扫描路由规则表，检查同一个关键词/动作是否出现在多个 Context → 出现则 fail |
| STR-05 | 统一语言表中无跨 Context 的同义词未标注 | 检查是否有相同术语出现在多个 Context 但"易混淆项"为空 → 为空则 fail |

### 关系合理性检查

| 规则编号 | 规则 | 判定方法 |
|---------|------|---------|
| STR-06 | 核心域不依赖支撑域/通用域的内部模型 | 在关系表中，如果核心域是下游且关系类型是 conformist → fail（核心域不应顺从非核心域） |
| STR-07 | 核心域对外暴露能力时使用 open-host-service | 如果核心域是上游但关系类型不是 OHS 或 published-language → warning |
| STR-08 | 关系表中无孤立 Context | 每个 Context 至少出现在关系表中一次（作为上游或下游）→ 未出现则 warning |
| STR-09 | shared-kernel 关系有正当理由 | 如果关系类型是 shared-kernel 但没有说明共享原因 → fail（shared-kernel 是强耦合，必须证明必要性） |

### 集成方式检查

| 规则编号 | 规则 | 判定方法 |
|---------|------|---------|
| STR-10 | 异步事件的数据流向字段不为空 | 集成方式为 event 时检查"数据流向"字段 → 为空则 fail |
| STR-11 | 同步调用有失败策略 | 集成方式为 api 时检查"失败策略"字段 → 为空则 fail |
| STR-12 | shared-db 必须有理由且限定范围 | 集成方式为 shared-db → 如果没有额外说明共享哪些表以及为什么不用事件 → fail |
| STR-13 | 核心域之间避免同步调用 | 两个核心域之间的集成方式为 api → warning（应考虑用事件解耦） |

### 路由规则检查

| 规则编号 | 规则 | 判定方法 |
|---------|------|---------|
| STR-14 | 每条路由规则都有"不归属"标注 | 检查"不归属"列是否为空 → 为空则 warning（没有辨析容易误判） |
| STR-15 | 路由规则无矛盾 | 检查是否存在同一个关键词在路由规则中归属 A，但在另一条规则的"不归属"中也提到 A → 矛盾则 fail |

### 领域类型检查

| 规则编号 | 规则 | 判定方法 |
|---------|------|---------|
| STR-16 | 核心域不超过总 Context 数的 40% | 数核心域数量 / 总 Context 数 → >40% 则 warning（核心域太多说明没区分重点） |
| STR-17 | 每个 Context 的领域类型都有判定理由 | "领域类型判定理由"字段为空 → fail |

## 评判优先级

当规则之间冲突时，按以下优先级裁决：

1. **单一归属 > 完备性** — 宁可漏一个概念未归属，也不要一个概念归属两个 Context
2. **核心域保护 > 关系简洁** — 宁可多加一层 ACL，也不要让核心域依赖外部模型
3. **异步解耦 > 实时响应** — 除非业务明确要求实时（<100ms），否则默认用事件
4. **明确拒绝 > 模糊包含** — "不负责什么"比"负责什么"更重要，边界靠排除来定义
